## О проекте

В этом README я оставлю некоторые выводы, которые у меня получились в ходе разработки.

Это мой первый проект на C#/Avalonia, в котором я решил использовал Claude как тьютора и ментора. Главной задачей было с помощью ИИ-ассистента разработать приложение простое по функционалу, но приближенное к правдоподобной архитектуре с правдоподобными задачами. 

Хоть у меня и нет опыта разработки нативных/кросс-платформенных приложений, но есть опыт разработки Web-приложений на PHP/Laravel и понимание работы фронтенда, что немного помогало.

## Проблемы и решения

### Masonry Grid

Отдал решение полностью Claude, так как задача была усложнена тем, что я решил сделать ещё и адаптивную сетку (флешбеки с веб-разработки). Впоследствии в базовый грид была добавил логику с анимированием с прицелом под перетаскивание.

### Drag'n'Drop

Писал с подсказками Claude, но основная суть: регистрация основных событий, запоминание перетаскиваемого объекта, определение, что элемент сдвинулся достаточно, чтобы начать перетаскивание, сдвиг прочих карточек, фиксация положения при отпускании мыши.

Неочевидный нюанс: пришлось события на клики менять на `Tapped` в `TaskListCardView` из-за конфликта между нажатием для перетаскивания и нажатием для открытия детального экрана таски.

### MVVM и Store

Изначально действовал по простой логике веб-приложений: при изменении списка (создание, удаление, обновление, реордер) легче загрузить из БД ещё раз и «обновить страницу».

Быстро понял, что это ошибочное решение — при таком обновлении возможны утечки памяти, кривое отображение анимаций из-за побитых ссылок и ворох других проблем. В отличие от веба здесь есть состояние приложения, чем неплохо бы начать использовать.

Если модель – это представление данных, а репозиторий – слой, который ходит в БД, нужен был промежуточный слой, который был бы источником правды для VM, что-то вроде кэша. Вспомнил, что фронты для такого используют store, и обнаружил, что это укладывается в концепцию MVVM, когда нужен один источник данных для разрозненных кусков приложения.

В вопросе организации store Claude показал себя хуже всего: предложить устоявшуюся концепцию реализации Store или какой-то гайдлайн сообщества он не смог.

Последним решением вынес сторы в статические свойства App для легкого доступа из любой VM, но не все необходимые рефакторы были сделаны.

### Дизайн

Дизайн делался экспромтом, без макета. Смысл такого нелепого розового дизайна прост – максимальная утилизация шрифтов, фонового изображения, иконок, хотелось посмотреть и потрогать как можно больше.

### Модалка и уведомления

Модалка сделана как отдельный layout поверх существующего layout приложения. Принимает в себя любой контент, что позволяет использовать её универсально; в приложении — для формы и детального экрана таски. Для передачи контента и закрытия используются сообщения.

Основная проблема этого layout — выглядит как калька с веб-приложения, стоило бы заюзать диалоговые окна.

Уведомление сделано так же — компонентом поверх основного layout. Само уведомление передаётся сообщением, автозакрытие настроено.

### Локализация

Захотелось динамическую локализацию, чтобы ознакомиться с работой местного `.resx`. По ходу стало понятно, что смена языка не происходит реактивно, поэтому с помощью Claude был написан `Localizer.cs`: меняет `CultureInfo` и `CultureUIInfo`, цепляет нужный ресурс и триггерит событие изменения.

Также для сокращения привязок был сделан класс `Tr`, но это решение не очень хорошо работает с динамическим `Status` – идей, как улучшить, пока нет.

### CI/CD

Полностью отдал Claude, так как было любопытно посмотреть, как вообще это заработает. Принял решение билдить под все ОС на x86_64 и arm64, благо сборка есть под каждую цель.

Пока слабо ориентируюсь в том, что он написал, — в процессе изучения.

### Тесты

Есть как проект. Знаю, что Avalonia предоставляет возможности для UI-тестов, но пока вообще не касался.

## Сборка приложения

### Сборщики

**Примечание**: Проверял работу приложения на MacOS и Linux. Windows проверял через Proton, так как рабочей машины на Windows нет. Ни одну ARM-сборку не проверял вообще.

```
./TodoAvalonia/Packaging/{build-mac.sh|build-win.sh|build-linux.sh} <x64|arm64> [версия] [отображаемое имя]
```

Версия не передана - берётся `<Version>` из `.csproj`. Отображаемое имя не передано — берётся имя сборки. Результат кладётся в `TodoAvalonia/Publish`.

Где что собирается:

- `build-win.sh` — с любой машины, родных утилит Windows не нужно.
- `build-mac.sh` — только на macOS: нужны `codesign`, `hdiutil`, `iconutil`.
- `build-linux.sh` — только на Linux и с `appimagetool` в `PATH`. Архитектура сборки должна совпадать с машиной: `appimagetool` родной, `aarch64` на x86 не соберётся.

Linux-версию с не-Linux машины можно собрать Docker-сборщиком (только x64, делал для теста):

```
./TodoAvalonia/Packaging/build-linux-docker.sh x64 [версия] [отображаемое имя]
```

### Windows

Скрипты на bash, значит нужен Git Bash или WSL. Без них остаётся

```
dotnet publish
```

но это обычная публикация: не одним файлом и с зависимостью от установленного .NET. Ключи, которыми собирается одиночный `.exe`, лежат в `build-win.sh`.
